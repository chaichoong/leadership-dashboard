### 4a — the check that reported a pass it could not fail

[js/cfv.js:671](js/cfv.js:671), *"Sidebar CFV badges in sync with detection"*. It computed an
unactioned count and an actioned count, then returned:

> `{ status: 'pass', detail: '… sidebar badges match' }`

unconditionally. It never looked at the badge. The words "sidebar badges match" were a string, not a
finding.

**It also disagreed with the badge it claimed to verify.** Two different dismissal rules:

| | Rule |
|---|---|
| Render / badge path ([js/cfv.js:216](js/cfv.js:216)) | only `potential` entries are dismissable |
| The health check ([js/cfv.js:673](js/cfv.js:673)) | `cfv` **and** `potential` are dismissable |

A confirmed CFV always counts toward the badge, by design. The check would have excluded one
carrying a stale dismissal key — a key that is only ever cleared inside the `potential` branch
([js/cfv.js:425](js/cfv.js:425)), so it survives an escalation from potential to confirmed. The
check's number could then sit below the badge and it would still print "match".

**Measured live before changing anything.** Detection returns 28 entries: 23 potential, 4 cfv,
1 cfv actioned. Render filter → 26 unactioned, 1 actioned. Badge DOM → red 26, orange 1. Zero
confirmed CFVs currently carry a dismissal key, so **the platform is right today** and the two
filters happen to agree. The defect is in the check, and it is latent rather than live.

Fixed, and **back-tested both ways through the real page**, not in isolation:

| Badge state | Sync bar rollup |
|---|---|
| Correct (26 / 1) | **6/6 checks ✓** |
| Forced stale (99 / 1) | **5/6 checks ✗** — "Sidebar shows 99 unactioned · 1 actioned, detection says 26 · 1 — badge is stale" |

On the old code the same corruption still returned 6/6. That is the proof the control was inert.

*A note on how nearly this was mis-reported:* the first back-test showed 6/6 in **both** states and
looked like the fix had not worked. The page was still running `js/cfv.js?v=27` from browser cache.
Only after a hard reload onto `v=28` did the failure appear. A cached asset makes a working fix look
broken just as easily as it makes a broken one look fixed.

### 4d — the spec was wrong, not the platform

The task spec says `cfv_*` localStorage keys "should be valid JSON". **They are not, and never have
been.** [js/cfv.js:782](js/cfv.js:782) writes `.toISOString()` strings; [js/cfv.js:294](js/cfv.js:294)
reads them back with `new Date(str)`. JSON is not involved anywhere in that path.

Run as specified, the check failed on 6 of 6 keys — a false defect on a healthy platform. Run
correctly (`!isNaN(new Date(v).getTime())`): **28 of 28 keys are valid ISO-8601 timestamps, 0 bad.**

This is the mirror image of yesterday's select-choice problem. That check could never fail; this one
could never pass. Both were checks measuring the wrong property, and both reported confidently.
The spec is corrected (§5).
