including a trivial read (`PAGE_REGISTRY.map(p => p.id)`) with no token in it. The token could
therefore not be injected into `localStorage._dlr_pat`, so the app ran logged out for the whole walk.

Per the skill, the token was **not** typed into the login field and **not** placed in any URL or
served file. This is a recurrence of the already-open finding
**`20260808-prod-e2e-sweep-023`** ("Scheduled sweep cannot authenticate: token injection blocked by
the permission classifier"), now three runs old. No new finding filed — the queue already has it.

**What this means for every tab result below:** a clean click and a clean console do NOT prove the
tab works. Data rendering went unchecked. Everything is UNVERIFIED, not PASS.

### Console errors observed
Three errors accumulated across the whole walk:

```
[error] Failed to load resource: the server responded with a status of 401   (x2)
[error] Uncaught (in promise) {error: Object}
```

Attribution work done:
- A **fresh tab loading the app cold returned ZERO console errors.** So the boot path is clean and
  all three came from walking tabs while logged out.
- The two 401s are Airtable calls made with no PAT (`Bearer null`) — the expected logged-out path,
  and the CEO Brief tab handled its 401 correctly with a visible error card and a Retry button
  (`js/ceo-brief.js:143-150`).
- The `Uncaught (in promise)` is an unhandled rejection carrying an Airtable error body. It could
  **not** be attributed to a specific tab without JS, and could not be reproduced authenticated.
  It is very likely only reachable logged out, which a real user never is. **Not filed as a
  finding** — an unattributable console line is not a confident code-change finding. Re-check it on
  the next FULL-mode run; if it appears while authenticated, it is real and should be filed then.
