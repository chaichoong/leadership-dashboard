`js/invoices.js:176` "Reconcile with Gmail" marks Paid every invoice whose email has left
`3: to pay` **and** restores to Unpaid every invoice whose email is in it — a bulk two-way write
behind one confirm dialog. The SOP documents only the read-only `?action=sync` refresh, and its
"Mismatch" troubleshooting entry (`:677`) sends the user to the *wrong* control for the exact
problem Reconcile was built to fix. Bulk select + bulk Mark Paid (`:780`, PATCHing in chunks of 10
then firing Gmail per thread) is undocumented too. This sits directly against the CLAUDE.md rule
"never mark legitimate unpaid items as paid without explicit reconcile logic".

### The one finding worth reading first

`20260809-drift-037`. The Airtable Tasks `Status` field offers **7** values — `Approval`,
`Overdue`, `Today`, `Upcoming`, `Completed`, `To do`, `Current` — while the page's
`STATUS_OPTIONS` (`os/tasks/index.html:844`) offers **5**. The grid handles the gap correctly
(`inlineSelectCell` at `:5325-5328` deliberately preserves a value not in the list). The **drawer**
(`:2753`) and drill-down modal (`:2590`) do not, so a task whose status is `To do` or `Current`
renders a select with nothing selected and the browser shows the first entry, `Today`.

Verified live today, with a control:

```
Status="To do"     → 10 records
Status="Current"   →  1 record
Status="Today"     → 65   (control)
Status="Approval"  → 57   (control)
```

The controls matter. The first attempt at this query returned 0 for **every** status because
`fields[]=Name` triggered `UNKNOWN_FIELD_NAME` and the error was swallowed — the exact silent-zero
trap CLAUDE.md describes. Only the control revealed it.

So 11 live tasks display a status they do not have. It is not write-corruption (`onchange` fires
only on a deliberate change), but a user is deciding from a wrong displayed value. Both the
drift-monitor and airtable-task-creator skills instruct writing `Status='To do'`, so this bucket
keeps being fed.
