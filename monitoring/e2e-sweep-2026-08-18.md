the sweep ran directly against production. The site is static, so this costs no signal.

### FAIL — `open-tasks-carry-no-completion-date` (1 violation)

Asserts: not completed => no Completion Date.
Regresses: *Aug 2026 — 143 open tasks carried a Completion Date, inflating monthly throughput.*

**This is a regression of a fix that was verified, not leftover data.** PR #76 (11 Aug)
closed three reopen paths, cleared all 88 stale stamps, and the invariant went green. The
offending stamp is dated **17 Aug** — six days later. The write path is live again.

Record `recnE11fJ7kzenaHq` — "INBOUND: Fwd: 1406 OLDHAM ROAD M40 XXX"
Status `Today`, Is Completed `0`, Completion Date `2026-08-17T07:38:38.299Z`,
Completed Month `2026-08`.

**Where the stamp came from (proved, not inferred):** `Approved At` is millisecond-identical
to `Completion Date` (both `2026-08-17T07:38:38.299Z`) with `Approval Outcome = Rejected`.
Both approval implementations stamp on a Rejected outcome and set Status=Completed —
`scripts/slack-automation/approvals.js:631-632` and `os/tasks/index.html:3759`. That write is
correct and is not the bug.

**What is wrong:** something then moved the task to `Today` and left the stamp behind.
`tests/completion-stamp-cleared-on-reopen.test.js` asserts the clear in exactly three
hardcoded files. `scripts/slack-automation/contractor-bot.js` is a **fourth** writer of
reopen statuses and never touches the completion field at all — `executeConfirmedInProgress`
(line 1475) writes `{status:'Today'}` with no clear, and the file defines no completion field
id anywhere. The test cannot see a new leak by construction.

**Ruled out by reading:** the Airtable automation is off (proved by the PR #76 probe);
`AUTOMATION PORT #1` in `os/tasks/index.html` does clear on flip-away, and its `task.completion`
guard is populated because `TASK_FIELD_IDS = Object.values(F)` includes `F.completion`.

**Honest gap:** I verified by reading that contractor-bot.js *can* reopen without clearing. I
did **not** prove it touched this record — the task is agent-owned (dept-operations), not an
obvious contractor job, so another untested reopener may exist. The test hole is real either way.

**Verification method:** violation formula `AND({Is Completed}=0,{Completion Date})` run with
full pagination → 1 row. Control `{Is Completed}=0` → 305 rows, so the query fires.
Worth recording: the ad-hoc form `{Completion Date}!=BLANK()` matched **all 305** open tasks —
the documented Airtable blank-field trap. Do not use it to size this.
