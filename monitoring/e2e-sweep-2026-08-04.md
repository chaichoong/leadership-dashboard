## Repo finding — the pre-push gate on main is flaky (not an app fault)

Committing this report hit a blocked push. `tests/sync-invariants/task-drawer-comments.spec.js`
fails under full-suite parallel load but passes in isolation, and **a different test in the file
fails on each run** — which is the repo's own stated signal for flakiness rather than a regression:

- Run 1 (full suite): 3 failed — lines 85, 121, 135. 109 passed.
- Isolated run of the whole spec: **5 passed**, 20.0s.
- Run 2 (full suite): 1 failed — line 156, a test that passed in run 1. 111 passed.

No `SKIP_SYNC_TESTS=1` bypass was used. The report was landed the sanctioned way: branch →
`gh pr create` → squash merge (PR #30).

Worth fixing, because a gate that goes red at random is the exact condition that tempts the
bypass CLAUDE.md warns against. The failing test at line 156 is the error-path case
("a failed comments fetch explains why and offers a retry"), and the timings suggest the spec
races a fetch/timeout rather than testing deterministically — it burned 20.4s before failing,
against ~3.5s for its passing siblings.

**RESOLVED same day.** Root cause: the spec stubbed only `api.airtable.com`, so every run
made real requests to `fonts.googleapis.com`, `fonts.gstatic.com` and `script.google.com`.
Proven by probe: delaying only those hosts made `waitForTask` time out at 20,011ms, matching
the observed 20.4s failure. This is a repeat of the 17 Jul 2026 incident; it came back because
the hermetic guard covered only the main shell at `/`, never the OS pages, and never specs
that roll their own Airtable mock. Fix: `stubExternalHosts()` is now the single place stubbing
third-party hosts (Apps Script and workers.dev moved into it), the spec calls it, and the
hermetic guard now walks `/os/tasks/index.html` and `/os/operations/index.html` too. Guard
back-tested by removing a stub and confirming it fails. Full suite: 114 passed, three
consecutive runs, ~1.1m each (was 3.3m with real network calls).
