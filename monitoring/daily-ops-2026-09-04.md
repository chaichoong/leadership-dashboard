Kevin, so items could sit unseen, and put a hand-merge of PR #163 on his list. Reading the live
worker rather than the week-old PR shows the opposite.

What the code on `origin/main` actually does today:

- `postPending()` **skips Kevin entirely** — `if (approver.key === 'kevin') { kevinHeld++; continue; }`.
  His per-task cards were retired in his 1 Sep 2026 notification contract. He receives none.
- His 08:00 digest goes by `openDm(env, KEVIN_SLACK_ID)` — a **direct message**, which always
  raises a Slack badge and a push. No mention required.
- Mica's cards also go by `openDm(env, approver.slackId)`. Also a DM. Also notifies.

So no live path posts an unmentioned message into a channel, except one narrow fallback: if
Mica's DM fails to open, her card routes to Kevin's channel, where it would indeed name nobody.
That is a rare edge, not the reported failure.

**Finding `20260814-daily-ops-146` is therefore dead.** It was real when filed on 14 Aug — 30
approvals sat unseen in a channel that pinged no one — but Kevin's own 1 Sep contract change
fixed it structurally by moving everyone onto DMs. The 28 Aug PR was written against the world
as it was on 27 Aug. Nobody noticed it had been overtaken, because a stuck PR gets re-listed
every morning without anyone re-reading what it does.

**The lesson worth keeping:** this routine reported a week-old PR's *description* as the current
state of production. The PR was listed as blocked every day and the block was accurate, so the
staleness never surfaced. A fix waiting long enough to be listed twice should be re-checked
against the live code before it is put on Kevin's list, not just re-counted.
