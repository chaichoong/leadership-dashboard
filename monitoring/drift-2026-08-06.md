### 4d was going to pass for the wrong reason

Even with keys present, the corrected 2026-08-03 assertion — *"every `cfv_*` value parses as a
valid Date"* — is too loose. `js/cfv.js` writes **two** value shapes:

| Shape | Keys | Written at |
|---|---|---|
| ISO timestamp | `cfv_dismissed_*`, `cfv_reflag_dismissed_*`, `*_chaseStart` | cfv.js:297, :797, :846, :876 |
| sentinel `'1'` | `*_returned`, `*_returnDismissed` | cfv.js:187, :763, :920 |

`new Date('1')` is **not** NaN — it returns 1 Jan 2001. Verified in-browser today. So the sentinel
keys sail through a blanket date check, and would still sail through if corrupted to any other
digit string. The check would report PASS while being blind to that half of the keys.

Fixed in the monitor's own spec: assert **by key shape**, and report the count checked per shape.

## 5. Actions Taken

### Auto-fixed — [PR #33](https://github.com/chaichoong/leadership-dashboard/pull/33), merged

**The fault.** `pageVer` auto-bumping depends on two hand-maintained lists that must match:

- `paths:` in `.github/workflows/auto-bump-pagever.yml` — decides whether the workflow **runs at all**
- `FILE_TO_PAGE` in `scripts/pre-commit-action.py` — decides **which page** a changed file bumps

Both carried a "keep this in sync" comment. **They were not in sync: 21 of 34 mapped files were
missing from the trigger list.** A push touching any of them never started the workflow, so
`pageVer` never moved.

It fails in the worst possible direction. Nothing errors. The workflow simply does not run, the
page keeps its old number, and every staleness signal built on `pageVer` — including section 3 of
this report — reads it as current.

Pages affected: `overview`, `cfv`, `tasks`, `wealth`, `money`, `income`, `costs`, `transactions`,
`skills`, `prospecting`, `kpi-library`, `ceo-brief`, `ar-variable`, `systemisation`, `os-team`,
`ai-brain`, `how-it-works`, `crm`.

**The near-miss worth naming.** `crm-supabase.html` was added to `FILE_TO_PAGE` on **1 August** to
fix this exact symptom. It changed nothing, because the missing half was the trigger filter. The
code comment there still describes the problem as solved. Adding a file to one list looks like a
fix and is not one.

**Changes merged:**

| File | Change |
|---|---|
| `.github/workflows/auto-bump-pagever.yml` | trigger list synced to `FILE_TO_PAGE` (34 entries). Dropped `os/business-plan-builder/index.html` — no mapping, no `PAGE_REGISTRY` id since the page was retired from the shell on 1 Aug, so it only ever started a no-op run |

**The test is the actual fix.** Two hand-maintained lists drift; a comment is not a control. The
new tests assert the lists are equal **in both directions**, and that every mapped page id exists
in `PAGE_REGISTRY`. They follow the file's existing convention of a control test that fails if
either list parses empty — otherwise a broken regex makes "the two lists are equal" trivially true
forever.

**Back-tested against the broken state**, per the repo rule that a new invariant must be shown to
fire: restoring the pre-fix workflow turns 3 of the 4 red, and the failure message names the files
that never bump.

**Confirmed working in production, not just asserted.** Minutes after PR #33 merged, PR #34 landed
a change to `js/reconciliation.js` — one of the 21 files that had never been able to trigger the
workflow. The action fired on its own and pushed commit `47f2463`, bumping the Leadership Dashboard
`pageVer` from **2.48 to 2.49**. Before this morning, that same push would have bumped nothing and
said nothing. Observed in the git log, not inferred.

## What this run says about the monitor itself

Three days running, the most useful finding has been about a watcher rather than the thing watched:
4 Aug found the dead-reference scan reading a fifth of the code; today found the version-bump
trigger covering 13 of 34 files and a 1 August fix to it that never took effect.

The shared pattern is a **silent no-op**. Nothing failed, nothing was logged, and the missing work
looked exactly like completed work. The counts in section 3 were identical yesterday and today, and
one of them was wrong both days.

Every check in this report should be read with the question *what would this look like if it were
not running at all* — and if the answer is "the same", it needs a control. That is why the vacuous
health checks are labelled vacuous rather than passed, and why the new tests fail when their own
input parses empty.
